# Kafka 与 RabbitMQ 性能对比实验方案

| 项目 | 内容 |
|---|---|
| 实验目标 | 在**完全相同的业务场景与参数**下，量化 Kafka 与 RabbitMQ 的吞吐、延迟、资源占用差异，为最终选型提供数据依据 |
| 被测系统 | 校园论坛异步链路（点赞事件、评论事件、秒杀下单） |
| 相关设计 | 《02-架构设计》第 6 节 消息抽象层；《03-功能设计》第 7 节 运维接口 |
| 文档版本 | V1.0 / 2026-09-14 |

---

## 1. 实验背景与目标

### 1.1 为什么需要这个实验

本项目在架构上同时实现了 Kafka 与 RabbitMQ 两套异步方案，业务代码通过统一抽象层调用。这不是"为了技术栈好看"，而是要回答一个具体的工程问题：

> **校园论坛的异步场景，到底该用哪个中间件？**

网上的对比文章大多是「Kafka 吞吐百万、RabbitMQ 吞吐十万」这类泛泛而谈，但真实选型需要考虑的是**当前场景的具体特征**：

- 点赞事件的单条消息很小（< 200 字节），但 QPS 峰值可达 5000
- 秒杀下单需要**延迟消息**（15 分钟超时取消），这是 RabbitMQ 的原生能力、Kafka 的短板
- 校园论坛的数据量远达不到 Kafka 的甜点区（百万级 QPS），Kafka 的优势可能根本发挥不出来
- 运维成本：Kafka 需要 ZooKeeper/KRaft + 多 Broker，RabbitMQ 单节点即可起步

**这些问题没有标准答案，只能实测。**

### 1.2 实验要回答的四个问题

| 编号 | 问题 | 判定指标 |
|---|---|---|
| Q1 | 在点赞场景（小消息、高 QPS）下，谁的吞吐更高？差异有多大？ | `produce_qps`、`consume_qps` |
| Q2 | 两种 MQ 的端到端延迟分布如何？秒杀场景下用户能感知到差别吗？ | P50/P95/P99 端到端延迟 |
| Q3 | 在相同硬件下，谁消耗的资源更少？ | CPU 峰值、内存峰值、Broker 磁盘占用 |
| Q4 | 面对本项目特有的**延迟消息**需求，Kafka 的模拟实现代价有多大？ | 延迟消息的准时率、CPU 开销 |

## 2. 被测对象：统一抽象层

**实验的公平性建立在抽象层之上**：两种 MQ 跑的是**同一份业务代码**，唯一变量是接口实现类。

```java
// 业务代码长这样 —— 完全不知道底下是哪个 MQ
@Service
@RequiredArgsConstructor
public class LikeServiceImpl implements LikeService {

    private final EventPublisher eventPublisher;   // 注入的是接口

    @Override
    public void like(Long userId, Integer targetType, Long targetId) {
        // ... Redis 判重与计数 ...

        eventPublisher.publish(LikeChangedEvent.builder()
            .messageId(idGenerator.nextId())
            .bizKey(String.format("like:%d:%d:%d", userId, targetType, targetId))
            .userId(userId)
            .targetType(targetType)
            .targetId(targetId)
            .action("LIKE")
            .timestamp(System.currentTimeMillis())
            .build());
    }
}
```

切换只改一行配置：

```yaml
forum:
  mq:
    provider: kafka      # ← 改成 rabbitmq，重启即完成切换
```

**这个设计使实验具备了严格的对照条件**：除了 MQ 本身，序列化方式、消息体大小、消费逻辑、幂等处理、埋点方式全部相同。

## 3. 两套实现的差异对照

### 3.1 架构模型差异

| 维度 | Kafka | RabbitMQ |
|---|---|---|
| 模型 | 分布式提交日志（Log） | 消息代理（Broker）+ 队列 |
| 消息存储 | 顺序追加到分区日志，消费者按 offset 拉取 | 存储在队列中，消费后（默认）删除 |
| 消费语义 | 消费者维护 offset，消息不因消费而删除 | 消息被消费并 ack 后从队列移除 |
| 回溯能力 | ✅ 可重置 offset 重新消费历史消息 | ❌ 消息已删除，无法回溯 |
| 路由能力 | 仅按 topic + partition 路由 | ✅ 四种 Exchange（direct/topic/fanout/headers），路由灵活 |
| 顺序性 | 分区内有序 | 队列内有序（单消费者） |
| 延迟消息 | ❌ 无原生支持 | ✅ 延迟插件或 TTL + DLX |

**对项目的影响**：Kafka 的「可回溯」能力在本项目无实际价值（业务不做重放）；Kafka 的「路由能力弱」也无影响（每个事件类型一个 topic 即可）。**RabbitMQ 的延迟消息是一张实打实的牌**，因为订单超时取消是刚需。

### 3.2 本项目各场景的适配度初判

| 场景 | 消息特征 | Kafka 适配度 | RabbitMQ 适配度 | 说明 |
|---|---|---|---|---|
| 点赞事件 `LIKE_CHANGED` | 小消息、QPS 峰值 5000、可容忍秒级延迟 | 高 | 中 | Kafka 的批量与顺序写优势明显；RabbitMQ 需靠 prefetch 与批量 ack 追赶 |
| 评论事件 `COMMENT_CREATED` | 小消息、低频（< 50 QPS） | 中 | 高 | 量小，两者都轻松胜任，RabbitMQ 的灵活路由更顺手 |
| 发帖事件 `POST_CREATED` | 低频、需要扇出（通知/索引/统计） | 中 | 高 | RabbitMQ 的 fanout Exchange 天然适合一对多 |
| **秒杀下单 `SECKILL_ORDER`** | **瞬时洪峰（10000 QPS 持续数秒）、绝不能丢** | **高** | 中 | Kafka 抗堆积能力强；RabbitMQ 内存压力大，需谨慎配置 |
| **订单超时 `ORDER_TIMEOUT`** | **延迟 15 分钟** | **低** | **高** | **Kafka 必须应用层模拟，这是最大差异点** |

**初步判断**：点赞与秒杀偏向 Kafka，延迟消息与扇出偏向 RabbitMQ。**最终结论需由实验数据支撑**，第 6 节给出决策矩阵。

## 4. 对比维度与方法论

### 4.1 对比维度

| 维度 | 具体指标 | 采集方式 |
|---|---|---|
| **吞吐** | 生产 QPS、消费 QPS、峰值 QPS | 压测工具计数 |
| **延迟** | P50 / P95 / P99 / Max 端到端延迟 | 消息头携带发送时间戳，消费端计算差值 |
| **可靠性** | 消息丢失数、重复投递数 | 发送总数 vs 处理总数比对 |
| **资源** | Broker CPU 峰值、内存峰值、磁盘峰值 | Prometheus 采集 |
| **稳定性** | 压测期间 QPS 波动系数、错误率 | 压测工具统计 |
| **延迟消息** | 准时率（实际触发时间与预期时间的偏差分布） | 专项测试 |
| **运维成本** | 部署节点数、配置复杂度、监控成熟度 | 主观评估 + 文档记录 |

### 4.2 端到端延迟的定义

这是本项目最重要的指标，定义必须精确：

```
生产端: t0 = System.currentTimeMillis()   // 构造事件时的时间戳
        t1 = 消息真正发出（KafkaTemplate.send 返回 / RabbitTemplate.convertAndSend 返回）

MQ:     消息在网络与 Broker 中传输、排队的时间

消费端: t2 = 消费者收到消息（@KafkaListener / @RabbitListener 方法进入）
        t3 = 业务处理完成

端到端延迟 = t2 - t0      （用户感知的「我点赞后，DB 多久更新」）
生产耗时   = t1 - t0
队列耗时   = t2 - t1
消费耗时   = t3 - t2      （记录在 t_mq_consume_log.cost_ms）
```

**必须在消息体中携带 `t0`**，不能只在消费端计时——那样测出的只是消费耗时，漏掉了排队时间，而排队时间恰恰是 MQ 差异最大的部分。

### 4.3 埋点实现

项目已内置埋点，无需压测工具额外统计：

```java
@Aspect
@Component
@RequiredArgsConstructor
public class MqConsumeMetricsAspect {

    private final MqConsumeLogMapper logMapper;

    @Around("@annotation(mqConsumer)")
    public Object around(ProceedingJoinPoint pjp, MqConsumer mqConsumer) throws Throwable {
        BaseEvent event = (BaseEvent) pjp.getArgs()[0];
        String provider = mqProperties.getProvider();
        long start = System.currentTimeMillis();

        try {
            Object result = pjp.proceed();
            long cost = System.currentTimeMillis() - start;

            logMapper.insert(MqConsumeLog.builder()
                .messageId(event.getMessageId())
                .consumerGroup(mqConsumer.group())
                .provider(provider)
                .topic(mqConsumer.topic())
                .bizType(event.getEventType())
                .status(1)
                .costMs((int) (start - event.getTimestamp()))   // ★ 端到端延迟
                .build());

            metrics.recordMqLatency(provider, mqConsumer.topic(), start - event.getTimestamp());
            return result;
        } catch (Throwable e) {
            // 记录失败...
            throw e;
        }
    }
}
```

**注意 `costMs` 存的是 `start - event.getTimestamp()`，即端到端延迟，而非单纯的业务处理耗时。** 这个定义在《04-数据库设计》第 4.8 节已说明，两个文档口径一致。

## 5. 压测方案

### 5.1 环境准备

**硬件（两组压测必须使用完全相同的硬件）**

| 角色 | 规格 | 数量 |
|---|---|---|
| 应用 + 压测客户端 | 8C 16G / SSD | 1 |
| MQ Broker | 8C 16G / SSD 500G | 3（Kafka）；3（RabbitMQ） |

**⚠️ 关键约束**：**Kafka 与 RabbitMQ 不得同时运行在同一台机器上**。两者都是 IO 密集型，同时运行会互相抢资源，导致数据完全不可比。必须分两轮独立进行，每轮结束后彻底清理环境（重启机器、清理磁盘）。

**软件版本**

| 组件 | 版本 |
|---|---|
| JDK | 21 (Temurin) |
| Kafka | 3.6.1（KRaft 模式，不启用 ZooKeeper 以减少变量） |
| RabbitMQ | 3.12.10 + Erlang 26 |
| MySQL / Redis | 被压测应用共用，配置相同 |

### 5.2 参数矩阵

**为了保证公平，两种 MQ 的参数必须映射到「等价语义」：**

| 语义 | Kafka 配置 | RabbitMQ 配置 |
|---|---|---|
| 分区/队列数 | `num.partitions=3` | 3 个队列，绑定到同一 Exchange |
| 副本/镜像 | `replication.factor=1`（单副本，先测基准） | 非镜像队列 |
| 生产者并发 | 32 线程 | 32 线程 |
| 批量大小 | `batch.size=16384`、`linger.ms=10` | `prefetchCount=250`、手动批量 ack |
| 确认级别 | `acks=1`（对比组：`acks=all`） | `publisher-confirm=correlated` |
| 消费并发 | `concurrency=4` | `concurrency=4`、`prefetch=250` |
| 消息持久化 | Kafka 天然持久化 | `delivery-mode=2`（持久化） |
| 消息大小 | 约 180 字节（`LikeChangedEvent` 的 JSON） | 同左 |

**固定变量清单**（每轮压测必须逐项核对）：

- [ ] 消息体大小与内容完全一致（用同一份 `LikeChangedEvent` JSON 模板）
- [ ] 压测并发数、持续时长、总消息数一致
- [ ] 应用 JVM 参数一致（`-Xms4g -Xmx4g -XX:+UseZGC`）
- [ ] Redis 与 MySQL 的连接池配置一致
- [ ] 消费端业务逻辑一致（同一份代码，仅 `provider` 不同）
- [ ] 环境温度相同（是的，SSD 在高温下会降速，建议每轮压测前机器静置 10 分钟）
- [ ] 每轮压测前重启应用与 Broker，清理 OS 页缓存

### 5.3 压测场景

#### 场景一：点赞事件吞吐（对应 Q1、Q2、Q3）

这是最核心的场景，因为点赞是论坛中 QPS 最高的异步操作。

```
目标: 持续发送 1,000,000 条 LikeChangedEvent
并发: 32 线程
时长: 约 3-5 分钟（取决于吞吐）
消息大小: 180 字节
消费端: 批量聚合，500ms 或 200 条刷一次库
```

| 轮次 | provider | 分区数 | 批次大小 | 确认级别 |
|---|---|---|---|---|
| 1-1 | kafka | 3 | 16384 | acks=1 |
| 1-2 | kafka | 3 | 32768 | acks=1 |
| 1-3 | kafka | 6 | 16384 | acks=1 |
| 1-4 | kafka | 3 | 16384 | acks=all |
| 2-1 | rabbitmq | 3 | prefetch=250 | confirm |
| 2-2 | rabbitmq | 3 | prefetch=500 | confirm |
| 2-3 | rabbitmq | 6 | prefetch=250 | confirm |
| 2-4 | rabbitmq | 3 | prefetch=250 | confirm + 持久化 |

**每轮重复 3 次，取中位数**（首次运行受 JIT 预热与页缓存影响，数据不可用，第一次结果直接丢弃）。

#### 场景二：秒杀下单洪峰（对应 Q1、Q3）

```
目标: 模拟秒杀开始瞬间，10,000 QPS 持续 10 秒
方法: 100,000 条 SECKILL_ORDER 事件在 10 秒内集中发送
消费端: 每条消息触发一次事务（创建订单 + 扣库存），不做批量
```

这个场景**刻意不做批量消费**，因为秒杀订单需要逐条处理（每条都要校验库存、可能触发回补）。这正是 RabbitMQ 相对 Kafka 可能更有优势的场景——**单条低延迟优于批量高吞吐**。

#### 场景三：延迟消息准时率（对应 Q4）

```
目标: 发送 10,000 条延迟 60 秒的消息，测量实际触发时间的分布
预期: 触发时间 - (发送时间 + 60s) 的偏差分布
```

| MQ | 实现方式 |
|---|---|
| RabbitMQ | 延迟插件 `rabbitmq_delayed_message_exchange` |
| Kafka | 应用层模拟：写入 `t_mq_message`（`next_retry_time = now + 60s`），时间轮扫描投递 |

**要测的**：Kafka 的模拟方案在 10,000 条延迟消息下的扫描开销（CPU 占用、扫描延迟）。如果偏差 P99 > 5 秒，说明该方案在消息量大时不可用，需要重新设计。

#### 场景四：消息可靠性（对应可靠性维度）

```
目标: 压测期间强制杀掉 Broker 的一个节点，观察消息丢失情况
方法: 三种 MQ 都在发送 50% 时 kill 掉一个 Broker，等待集群恢复
观察: 发送成功但未被消费的消息数量
```

| MQ | 预期表现 |
|---|---|
| Kafka（replication.factor=1） | 该分区的消息会丢失 |
| Kafka（replication.factor=3, acks=all） | 无丢失，但发送延迟上升 |
| RabbitMQ（非镜像） | 该队列的消息丢失 |
| RabbitMQ（镜像队列） | 无丢失，但吞吐下降 |

**这个场景的价值在于量化「可靠性 vs 性能」的取舍代价**——用副本换来的可靠性，究竟要付出多少吞吐。

### 5.4 压测执行步骤

```bash
#!/usr/bin/env bash
# benchmark.sh —— 单轮压测脚本

PROVIDER=$1          # kafka | rabbitmq
SCENARIO=$2          # LIKE_EVENT | SECKILL_ORDER | DELAY
CONCURRENCY=$3
TOTAL=$4
BATCH_NO="B$(date +%Y%m%d)-$(date +%H%M%S)"

echo "=== 压测开始 batch_no=${BATCH_NO} provider=${PROVIDER} ==="

# 1. 环境清理
docker compose -f docker-compose-${PROVIDER}.yml down -v
sleep 10
docker compose -f docker-compose-${PROVIDER}.yml up -d
sleep 30                              # 等待 Broker 完全就绪

# 2. 重启应用（切换 provider）
sed -i "s/provider: .*/provider: ${PROVIDER}/" src/main/resources/application-benchmark.yml
mvn -pl forum-boot spring-boot:run -Dspring-boot.run.profiles=benchmark &
sleep 45                              # 等待应用启动 + JIT 预热

# 3. 预热（丢弃首次结果）
curl -X POST localhost:8080/api/admin/mq/benchmark/start \
  -d "{\"scenario\":\"${SCENARIO}\",\"totalMessages\":10000,\"concurrency\":8}"
sleep 60

# 4. 正式压测
curl -X POST localhost:8080/api/admin/mq/benchmark/start \
  -d "{\"batchNo\":\"${BATCH_NO}\",\"scenario\":\"${SCENARIO}\",\
       \"totalMessages\":${TOTAL},\"concurrency\":${CONCURRENCY}}"

# 5. 等待消费完毕（backlog=0）
while true; do
  BACKLOG=$(curl -s localhost:8080/api/admin/mq/status | jq '.backlog')
  [ "$BACKLOG" -eq 0 ] && break
  sleep 5
done

# 6. 采集结果
curl -s "localhost:8080/api/admin/mq/benchmark/compare?batchNo=${BATCH_NO}" \
  > "results/${BATCH_NO}-${PROVIDER}-${SCENARIO}.json"

echo "=== 压测完成，结果已保存 ==="
```

### 5.5 结果记录

所有结果写入 `t_mq_benchmark_result` 表（结构见 `sql/01-schema.sql`）。查询对比：

```sql
-- 同批次下两种 MQ 的横向对比
SELECT
    scenario,
    concurrency,
    partition_count,
    batch_size,
    MAX(CASE WHEN provider = 'kafka'    THEN produce_qps END) AS kafka_produce,
    MAX(CASE WHEN provider = 'rabbitmq' THEN produce_qps END) AS rmq_produce,
    MAX(CASE WHEN provider = 'kafka'    THEN consume_qps END) AS kafka_consume,
    MAX(CASE WHEN provider = 'rabbitmq' THEN consume_qps END) AS rmq_consume,
    MAX(CASE WHEN provider = 'kafka'    THEN p99_ms END)      AS kafka_p99,
    MAX(CASE WHEN provider = 'rabbitmq' THEN p99_ms END)      AS rmq_p99,
    MAX(CASE WHEN provider = 'kafka'    THEN cpu_peak_pct END) AS kafka_cpu,
    MAX(CASE WHEN provider = 'rabbitmq' THEN cpu_peak_pct END) AS rmq_cpu

WHERE batch_no = 'B20260914-01'
GROUP BY scenario, concurrency, partition_count, batch_size;
```

同时从消费埋点表取延迟分布（两个数据源交叉验证）：

```sql
SELECT provider,
       COUNT(*)                     AS cnt,
       ROUND(AVG(cost_ms), 2)       AS avg_ms,
       ROUND(SUM(cost_ms <= 10)  / COUNT(*) * 100, 2) AS pct_le_10ms,
       ROUND(SUM(cost_ms <= 50)  / COUNT(*) * 100, 2) AS pct_le_50ms,
       ROUND(SUM(cost_ms <= 200) / COUNT(*) * 100, 2) AS pct_le_200ms,
       MAX(cost_ms)                 AS max_ms
FROM t_mq_consume_log
WHERE biz_type = 'LIKE_CHANGED'
GROUP BY provider;
```

## 6. 预期结果与决策矩阵

> ⚠️ **以下为基于公开基准与架构分析的预期值，不是实测数据。** 实际数值必须由第 5 节的压测产出，届时替换本节内容。在数据出来之前，任何"Kafka 比 RabbitMQ 快 N 倍"的说法都是猜测。

### 6.1 预期趋势（待验证）

| 指标 | 预期 Kafka | 预期 RabbitMQ | 预期差异原因 |
|---|---|---|---|
| 生产 QPS（小消息） | 较高 | 中等 | Kafka 顺序追加写 + 批量发送；RabbitMQ 逐条路由 + 确认 |
| 消费 QPS | 较高 | 中等 | Kafka 批量拉取；RabbitMQ 推送 + prefetch |
| P50 延迟 | 较高（10ms 级） | 较低（1ms 级） | Kafka 的 `linger.ms` 批量等待必然增加单条延迟；RabbitMQ 即时推送 |
| P99 延迟 | 较低（更稳定） | 较高（积压时飙升） | Kafka 抗堆积；RabbitMQ 积压后内存压力导致抖动 |
| CPU 占用 | 较低 | 较高 | RabbitMQ 的 Erlang VM 与逐条确认开销 |
| 磁盘占用 | 较高（保留策略） | 较低（消费即删） | Kafka 按时间/大小保留，RabbitMQ 消费后释放 |
| 延迟消息 | 需应用层模拟 | 原生支持 | 最大差异点 |

### 6.2 决策矩阵

实验完成后按下表打分（1–5 分），加权计算总分：

| 维度 | 权重 | 理由 | Kafka | RabbitMQ |
|---|---|---|---|---|

### 6.3 可能的结论与对应行动

| 若实验结果显示 | 则选型 | 理由 |
|---|---|---|
| Kafka 在点赞吞吐上领先 > 50%，且延迟消息模拟方案的 P99 偏差 < 2s | **Kafka** | 吞吐优势显著，延迟消息的短板可接受 |
| 两者的吞吐差距 < 30%，而 RabbitMQ 端到端延迟明显更低 | **RabbitMQ** | 校园论坛的量级下，Kafka 的吞吐优势发挥不出来，低延迟更实用 |

**倾向性说明**：考虑到校园论坛的实际量级（日活 < 5000，点赞峰值 5000 QPS）**远低于 Kafka 的性能甜点区**，且 Kafka 的延迟消息需要应用层模拟（增加复杂度和故障面），**本项目预期会选择 RabbitMQ 作为主用中间件**。但这个判断必须在实验数据出来后重新审视——如果实测显示 Kafka 在峰值场景下稳定性明显更好，这个倾向就应当被推翻。

**这正是做这个实验的意义：让数据推翻直觉。**

## 7. 实施与回滚

### 7.1 切换检查清单

切换前必须逐项确认：

- [ ] 旧 MQ 的 `backlog = 0`（所有消息已消费完毕）
- [ ] 本地消息表中 `status IN (0, 2)` 的记录数为 0（无待发送消息）
- [ ] 新 MQ 的 topic/queue 已创建，消费者组已就绪
- [ ] 新 MQ 的连接配置已写入配置中心并验证连通性
- [ ] 监控面板已切换到新 provider 的指标
- [ ] 回滚方案已准备（保留旧配置，5 分钟内可切回）

### 7.2 切换步骤

```bash
# 1. 确认旧 MQ 已清空
curl -s localhost:8080/api/admin/mq/status | jq '.backlog'   # 必须为 0

# 2. 逐个实例滚动切换（保证服务不中断）
for instance in app1 app2 app3; do
    # 修改该实例配置
    ssh $instance "sed -i 's/provider: kafka/provider: rabbitmq/' /opt/forum/application.yml"
    # 优雅下线（等待正在处理的消息完成）
    ssh $instance "curl -X POST localhost:8080/actuator/shutdown"
    sleep 30
    ssh $instance "systemctl start forum"
    sleep 60
    # 验证该实例正常
    ssh $instance "curl -s localhost:8080/actuator/health"
done

# 3. 全量验证
curl -s localhost:8080/api/admin/mq/status | jq '.provider'   # 应为 rabbitmq
```

### 7.3 回滚方案

```bash
# 回滚 = 反向执行切换步骤，预计耗时 < 5 分钟
for instance in app1 app2 app3; do
    ssh $instance "sed -i 's/provider: rabbitmq/provider: kafka/' /opt/forum/application.yml"
    ssh $instance "systemctl restart forum"
done
```

**回滚的安全性**：由于两种实现的业务语义完全一致（都保证 at-least-once + 消费端幂等），**切换点前后产生的消息不会产生数据不一致**。这是抽象层设计的核心价值——它不仅让切换容易，更让切换**安全**。

## 8. 实验之外：抽象层的长期价值

这个实验的直接产出是「选哪个 MQ」的答案，但抽象层本身的价值远超这一次选型：

| 价值 | 说明 |
|---|---|
| **降低试错成本** | 未来若要尝试 RocketMQ、Pulsar，只需新增一个实现类，业务代码零改动 |
| **局部替换** | 若某个场景（如秒杀）需要不同的 MQ，可只替换该场景的 Publisher 实现 |
| **测试友好** | 单元测试中可注入内存实现（`InMemoryEventPublisher`），无需启动真实 MQ |
| **约束设计** | 强制业务代码只依赖 `at-least-once` 这一最小语义，避免依赖某个 MQ 的特有能力而丧失可移植性 |
| **倒逼幂等** | 抽象层明确不提供 exactly-once，迫使每个消费者都必须实现幂等——这本来就是分布式系统的正确做法 |

**最后一条尤其重要**：很多人选择 Kafka 是冲着"exactly-once 语义"去的，但在真实系统中，跨 MQ + DB 的 exactly-once 几乎无法实现（除非使用 Kafka 事务并把 DB 也纳入事务范围，代价极高且限制很多）。**依赖 exactly-once 的代码，在换 MQ 或出现边界情况时必然出问题。** 抽象层强制 at-least-once + 幂等，是一道保护。
