## 1. 项目背景与目标

### 1.1 背景

校内信息长期散落在微信群、QQ 群、表白墙等封闭且不可检索的渠道中：一条失物招领信息在 500 人大群里 10 分钟后就被刷没，一份考研资料在群文件里反复上传下载。这些渠道共同的问题是**信息无法沉淀、无法检索、无法按主题归类**。

本项目的目标是为校内提供一个**结构化的信息交流平台**：信息按板块归类、按热度与时间排序、支持检索与互动沉淀，让一条有用的信息在发布一个月后仍然能被需要它的人找到。

### 1.2 目标

| 目标 | 衡量方式 |
|---|---|
| 信息可沉淀 | 帖子持久化 + 板块归类 + 全文检索可用 |
| 互动流畅 | 点赞、评论等高频操作 P99 延迟 < 100ms |
| 承载突发流量 | 秒杀场景峰值 10000 QPS 下不超卖、不雪崩 |
| 技术验证 | 同一套业务异步逻辑可在 Kafka / RabbitMQ 间零代码切换，并产出可对比的压测数据 |

### 1.3 本期范围

- **核心功能**：用户注册登录、板块浏览、发帖、点赞、评论、消息通知。
- **附加功能**：优惠券秒杀（Redis 预扣 + MQ 异步下单 + 超时回补）。
- **用户运营**：每日签到领积分、月度全勤额外奖励、积分商城兑换。
- **技术专项**：可插拔消息中间件抽象层 + Kafka/RabbitMQ 性能对比实验。

**明确不做（本期）**：私信聊天、直播、付费内容、视频转码、推荐算法个性化排序。

> **积分与商城为什么算「用户运营」而不是「附加功能」：**
> 秒杀解决的是「同一时刻的并发争抢」，商城解决的是「长期的行为激励」，两者的技术难点完全不同
> ——前者要抗瞬时峰值，后者要保证一本不能算错的账。
> 把签到做成积分体系的入口，是因为签到是**唯一一个每天都必然产生写入**的用户行为，
> 用它来验证「Redis 位图 + MySQL 真相」这套组合，比用一个人为构造的场景更有说服力。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| 板块（Board） | 帖子的**唯一归属**分类，一个帖子只属于一个板块，如「学习交流」 |
| 标签（Tag） | 帖子的**交叉标注**，一个帖子可以有多个，如「考研」「组队」 |
| 一级评论 | 直接回复帖子的评论，拥有楼层号 |
| 二级评论 | 回复某条评论的评论（楼中楼），归属到某个一级评论下，最多两层 |
| 点赞目标 | 被点赞的对象，类型为帖子或评论 |
| 热度分 | 综合点赞、评论、收藏数与时间衰减计算的排序权重 |
| 秒杀活动 | 限时限量的优惠券发放场次 |
| 用户券 | 用户实际持有的一张券，是优惠券模板的实例 |
| 逻辑真相 | 本项目中特指 **Redis 中的实时计数**，与 DB 中的冗余计数相对 |
| 最终真相 | 本项目中特指 **MySQL 中的持久化数据**，是容灾与对账的基准 |
| 签到位图 | 每个用户每月一个 Redis Bitmap，第 N 位表示当月第 N 天是否签到 |
| 积分账户 | 用户的积分余额与累计获得/消耗，一个用户一条记录 |
| 积分流水 | 每一次积分变动的不可变记录，是账户余额的唯一解释来源 |
| 全勤奖励 | 当月签到天数超过阈值（默认 25 天）时额外发放的积分 |
| 商城商品 | 可用积分兑换的物品，分优惠券 / 实物 / 虚拟物品三类 |
| 兑换订单 | 用户用积分兑换商品产生的记录，是积分消耗的凭证 |

## 3. 干系人与角色

| 角色 | 说明 | 核心诉求 |
|---|---|---|
| 游客 | 未登录用户 | 浏览帖子列表与详情、搜索、注册 |
| 普通用户 | 已注册的在校学生 | 发帖、评论、点赞、收藏、关注、领券、签到、兑换积分商品、接收通知 |
| 版主 | 负责单个板块的用户 | 删除/置顶/加精本板块帖子、处理举报 |
| 管理员 | 系统运营人员 | 全站内容管理、用户封禁、板块与标签管理、优惠券与秒杀活动配置、**商城商品与兑换订单管理** |
| 运营人员 | 组织秒杀活动 | 配置券模板、创建秒杀场次、查看活动数据 |

**权限模型**：基于角色的访问控制（RBAC），角色为 `普通用户(0) < 版主(1) < 管理员(2)` 三级包含关系。权限校验点分三层：

1. **接口层**：按 URL 前缀区分（`/api/admin/**` 需管理员）——**实际实现是拦截器 + `@RequireRole` 注解，不是 Spring Security**（见《02-架构设计》ADR-009）。
2. **资源层**：版主只能操作自己负责板块的资源，通过 `t_board.owner_id` 判定。
3. **数据层**：只能操作自己创建的资源（如删除自己的帖子、取消自己的兑换订单）。

> **积分与商城模块是权限模型最容易失守的地方**，因为它是第一个「管理端要写、用户端只读」的模块
> ——帖子、评论是「人人可写自己的」，秒杀是「人人可下单」，
> 只有商城存在「用户能看到但绝不能改」的数据。
> 因此它的全部管理接口一律置于 `/api/admin/**` 前缀之下，由接口层统一拦截，
> 业务代码里不出现任何角色判断（理由见 4.6.4）。

### 4.2 核心用例：发帖

| 项 | 内容 |
|---|---|
| 用例编号 | UC-POST-01 |
| 参与者 | 普通用户 |
| 前置条件 | 已登录；账号状态正常（未禁言/封禁）；目标板块状态为「正常」 |
| 后置条件 | 帖子以「已发布」或「待审核」状态落库；作者发帖数 +1；关注者收到通知 |

**主流程**：

1. 用户进入发帖页，选择板块，填写标题与正文，可选填标签、上传图片。
2. 前端做前置校验：标题 5–128 字符、正文 10–50000 字符、图片不超过 9 张且单张 ≤ 5MB。
3. 前端每 30 秒将草稿写入 localStorage；用户可手动「保存草稿」调用服务端草稿接口。
4. 用户点击发布，请求携带幂等令牌（防止重复提交）。
5. 服务端校验：登录态 → 账号状态 → 板块状态与发帖权限 → 参数合法性。
6. 敏感词检测：命中则拒绝并返回具体违禁词位置。
7. 内容入库（`t_post` + `t_post_content` 同一事务），状态由板块的 `post_audit` 决定：
   - 免审板块 → `status=1`（已发布），写 `publish_time`
   - 需审板块 → `status=2`（待审核）
8. 事务提交后发起异步动作（**不阻塞响应**）：
   - 写本地消息表 → 投递 `POST_CREATED` 事件
   - 消费者：更新作者发帖数、板块帖子数、抽取标签计数、向关注者推送通知、清除相关缓存
9. 返回帖子 ID，前端跳转详情页。

**异常流程**：

| 场景 | 处理 |
|---|---|
| 幂等令牌已使用 | 返回上次创建的帖子 ID，不重复创建 |
| 敏感词命中 | 返回 400 + 命中词位置，内容不落库 |
| 板块已关闭 | 返回 403，提示「该板块当前禁止发帖」 |
| 用户被禁言 | 返回 403，提示禁言到期时间 |
| 正文含外链过多（>5 条） | 转人工审核（`status=2`），并在审核意见中标注 |

### 4.3 核心用例：点赞

| 项 | 内容 |
|---|---|
| 用例编号 | UC-LIKE-01 |
| 参与者 | 普通用户 |
| 前置条件 | 已登录；目标帖子/评论存在且未被删除 |
| 后置条件 | 点赞关系建立；目标点赞数 +1（Redis 立即生效，DB 异步跟上） |

**主流程**：

1. 用户在帖子/评论上点击点赞按钮（前端乐观更新 UI，按钮立即变为已点赞态）。
2. 前端发送请求，携带目标类型与目标 ID。
3. 服务端校验登录态与目标有效性。
4. **Redis 原子判重**：`SADD like:target:{type}:{id} {userId}`
   - 返回 `1` → 本次是新增点赞，继续
   - 返回 `0` → 已点赞，直接返回成功（幂等，不报错）
5. **同一 Lua 脚本内**完成：点赞集合写入 + 点赞计数 `INCR`。
6. 写本地消息表，投递 `LIKE_CHANGED` 事件（含 `action=LIKE/UNLIKE`）。
7. 立即返回成功（**不等待 DB 写入**）。
8. 消费者批量聚合（默认 500ms 或 200 条触发一次刷写）：
   - 批量 INSERT/DELETE `t_user_like`
   - 批量 UPDATE `t_post.like_count` / `t_comment.like_count`
   - 按目标作者聚合写通知

**异常与边界**：

| 场景 | 处理 |
|---|---|
| 重复点赞 | Redis `SADD` 返回 0，直接返回成功（幂等） |
| 点赞自己的内容 | 允许，但**不产生通知** |
| 目标已被删除 | 返回 404，并清理 Redis 中的孤儿点赞数据 |
| Redis 不可用 | 降级：直接写 DB（`uk_user_target` 保证幂等），记录告警 |
| MQ 不可用 | 消息留在本地消息表，由投递线程重试，点赞在 Redis 中已生效 |
| 消费者重复消费 | `uk_user_target` 唯一索引拦截，捕获 `DuplicateKeyException` 后忽略 |

**取消点赞**：与点赞互为逆操作，`SREM` + `DECR`，投递 `action=UNLIKE` 事件。

### 4.4 核心用例：评论

| 项 | 内容 |
|---|---|
| 用例编号 | UC-COMMENT-01 |
| 参与者 | 普通用户 |
| 前置条件 | 已登录；帖子状态为「已发布」且未关闭评论 |

**主流程**：

1. 用户在帖子详情页输入评论内容，点击发送。
2. 服务端校验登录态、账号状态、帖子状态、内容长度（1–1000 字）。
3. 敏感词检测。
4. **同步写库**（与点赞的异步策略相反，理由见下）：
   - 一级评论：`root_id=0, parent_id=0, level=1`，楼层号由 Redis `INCR comment:floor:{postId}` 生成
   - 二级评论：`root_id=所属一级评论ID, parent_id=被回复评论ID, level=2, floor=0`
   - 同一事务内更新 `t_post.comment_count`、`t_post.last_comment_time`；二级评论另需更新根评论的 `reply_count`
5. 事务提交后异步：
   - 通知被评论者/被回复者（自己评论自己不通知）
   - 重算帖子热度分
   - 清除帖子详情缓存

**为什么评论同步落库而点赞异步？**

这是本项目的关键设计判断，二者性质不同：

| 维度 | 点赞 | 评论 |
|---|---|---|
| 内容载体 | 无内容，仅一个关系 | 用户创作的文本，**不可丢失** |
| 频率 | 单帖可达数万次 | 单帖通常几十条 |
| 失败后果 | 丢一次点赞，用户可重试 | 丢一条用户辛苦写的内容，不可接受 |
| 幂等性 | 天然幂等（唯一索引） | 不幂等，重复即产生重复内容 |
| 一致性要求 | 最终一致即可 | 需强一致（评论完立刻要能看到） |

结论：**点赞走异步削峰，评论走同步保一致**，异步只用于评论的衍生动作（通知、热度、缓存失效）。

### 4.5 核心用例：积分秒杀

| 项 | 内容 |
|---|---|
| 用例编号 | UC-SECKILL-01 |
| 参与者 | 普通用户 |
| 前置条件 | 已登录；活动处于「进行中」且已预热；用户未超过限购 |
| 后置条件 | 生成一笔待支付订单；库存扣减；15 分钟内未支付则自动关闭并回补库存 |

> **与积分商城的边界**：本用例卖的是限时抢购的商品，支付用积分；普通兑换见 4.6。两者的分界线是「有没有流量洪峰」，理由见《02-架构设计》ADR-010。

**主流程**：

1. 活动开始前 N 分钟（`warmup_minutes`），定时任务将活动库存预热到 Redis：
   `SETNX seckill:stock:{activityId} {available_stock}`（**必须是 `SETNX`**，用 `SET` 会被每分钟的执行不断重置回初始值 → 超卖）
2. 用户点击「立即抢购」。
3. **Redis Lua 脚本原子执行**（这是抗洪峰的核心，单线程原子，无锁无竞争）：
   ```lua
   -- KEYS[1] = seckill:stock:{activityId}            剩余库存
   -- KEYS[2] = seckill:bought:{activityId}           已抢用户 Hash
   -- KEYS[3] = seckill:order:{activityId}:{userId}   该用户的 orderNo
   -- KEYS[4] = seckill:order:no:{yyyyMMdd}           日内序号
   -- ARGV[1] = userId   ARGV[2] = perUserLimit   ARGV[3] = 订单号前缀
   local existed = redis.call('GET', KEYS[3])
   if existed then
       return {tonumber(redis.call('GET', KEYS[1]) or '0'), existed}   -- 幂等重放，返回同一张单
   end
   local stock = redis.call('GET', KEYS[1])
   if stock == false then
       return {-3}        -- 未预热（不是「抢光」，对用户是两种不同的提示）
   end
   if tonumber(redis.call('HGET', KEYS[2], ARGV[1]) or '0') >= tonumber(ARGV[2]) then
       return {-2}        -- 已达限购
   end
   if tonumber(stock) <= 0 then
       return {-1}        -- 库存不足
   end
   local seq = redis.call('INCR', KEYS[4])
   local orderNo = ARGV[3] .. string.format('%06d', seq)
   redis.call('DECR', KEYS[1])
   redis.call('HINCRBY', KEYS[2], ARGV[1], 1)
   redis.call('SET', KEYS[3], orderNo)
   return {tonumber(stock) - 1, orderNo}
   ```
4. Lua 返回成功 → 写本地消息表并投递 `SECKILL_ORDER` 事件，**立即返回「排队中」+ orderNo**。
5. Lua 返回 `-1` → 返回「已抢光」；`-2` → 「您已参与过本场活动」；`-3` → 「活动太火爆，请稍后再试」。
6. 消费者收到消息后异步落库：
   - 开启事务：扣减 `t_seckill_activity.available_stock`、增加 `locked_stock`，再插入 `t_seckill_order`（`status=0` 待支付）
   - 库存扣减使用 `UPDATE ... SET available_stock = available_stock - 1 WHERE id = ? AND available_stock >= 1`，
     以 `affectedRows` 判断是否成功，作为 **DB 层防超卖的兜底**
   - 若影响 0 行（Redis 与 DB 漂移）或 `uk_user_activity` 冲突 → 回补 Redis 库存并记录告警，**不重试**
7. 前端按 orderNo 轮询结果，成功后进入支付页。
8. 用户支付 → **扣积分（`WHERE balance >= ?`，此时才扣）** → 订单 `status=1`，`locked_stock` 转 `sold_count`。
9. 支付超时（默认 15 分钟）→ 由延迟消息触发取消（定时扫描兜底）：
    - 订单 `status=3`（超时关闭）
    - `locked_stock` 回补到 `available_stock`
    - **Redis 库存 `INCR` 回补**
    - **不删除 `seckill:bought` 里的用户标记**——「每人限购 1 件」是活动期内的一次性资格，取消不退还资格

**异常与边界**：

| 场景 | 处理 |
|---|---|
| 活动未开始 / 已结束 | 返回 400，前端按钮应已置灰，此为服务端二次校验 |
| 用户疯狂点击 | 前端按钮点击后立即置灰 + 服务端 Redis 判重，双重防护 |
| Redis 挂了 | **降级为拒绝请求**（返回「活动太火爆，请稍后再试」），绝不降级为直接查库，否则 DB 会被打死 |
| MQ 积压 | 前端展示「排队中」，订单最终会创建；积压超阈值触发告警 |
| 消费者重复消费 | `uk_user_activity` + `t_mq_consume_log` 双重幂等 |
| Redis 与 DB 库存不一致 | 每 5 分钟对账任务比对，以 DB 为准修正 Redis，并告警 |
| 用户下单后不支付 | 延迟消息 15 分钟后触发取消与回补 |
| 一人多单（限购 > 1） | 当前设计限定 `per_user_limit=1`；若需放开，见《04-数据库设计》的索引调整说明 |

### 4.6 核心用例：签到与积分兑换

签到与兑换在实现上分属两条链路，但在业务上共用同一本账，故合并为一个用例描述。

#### 4.6.1 UC-POINTS-01 每日签到

| 项 | 内容 |
|---|---|
| 用例编号 | UC-POINTS-01 |
| 参与者 | 普通用户 |
| 前置条件 | 已登录 |
| 后置条件 | 用户当日签到成功，积分 +N；同一自然日内重复请求不再发分 |

**规则**：

| 规则 | 值 | 说明 |
|---|---|---|
| 每日签到积分 | 5 分 | 可配置（`forum.points.signin-points`） |
| 签到周期 | 自然日（Asia/Shanghai） | 以**服务器时区**为准，不信任客户端时间 |
| 同一用户同一天 | 只能签一次 | 幂等，重复请求返回「今日已签到」而非报错 |
| 月度全勤阈值 | 当月签到 **> 25 天**（即 ≥ 26 天） | 可配置（`forum.points.bonus-threshold`） |
| 月度全勤奖励 | 100 分 | 次月 1 日结算上月，一次性发放 |

**主流程**：

1. 用户进入积分页，前端请求 `GET /api/points/signin/status?month=YYYY-MM`，
   返回本月已签日期集合、今日是否已签、连续签到天数。
2. 用户点击「签到」，`POST /api/points/signin`。
3. **Redis Bitmap 原子置位**（核心步骤）：
   对 key `forum:points:signin:{userId}:{yyyyMM}` 执行 `SETBIT key (day-1) 1`，
   **用返回值判断**——返回 `0` 表示此前未签（本次有效），返回 `1` 表示今日已签（幂等返回）。
   首次置位时设置 70 天 TTL。
4. 置位成功 → 开启事务：写 `t_user_signin`、`t_user_points` 加分、`t_points_record` 记流水。
5. 返回本次获得积分与最新余额。

**为什么用 Bitmap 而不是 `SET` 或数据库：**

| 方案 | 单用户单月存储 | 判断「今天签了吗」 | 统计「本月签了几天」 | 问题 |
|---|---|---|---|---|
| MySQL 单行 | ~50 B（含索引开销） | 一次主键查询 | `COUNT(*)`，需索引扫描 | 每天每人一次写入，热点集中 |
| Redis `SET` | 31 个成员 × ~50 B ≈ 1.5 KB | `SISMEMBER` | `SCARD` | 存储是位图的 **375 倍** |
| **Redis Bitmap** | **4 B**（31 位） | `GETBIT` | `BITCOUNT` | 无 |

位图的价值不只是省内存，更在于**一条命令同时完成「判断」和「写入」**：
`SETBIT` 返回旧值，`prev == 0` 即「本次是首次签到」。
若用 `GETBIT` + `SETBIT` 两步，两个并发请求会双双读到 0，都需要靠数据库唯一索引兜底
——那意味着并发时必然有一个请求以「抛异常」结束，而不是优雅地返回「已签到」。

**异常与边界**：

| 场景 | 处理 |
|---|---|
| 重复签到 | `SETBIT` 返回 1 → 返回「今日已签到」（错误码 16001），**不是异常** |
| Redis 不可用 | 降级为**直接写数据库 + 唯一索引判重**（签到是低频操作，DB 扛得住；这与秒杀必须拒绝请求的降级策略相反） |
| 位图已置位但事务回滚 | 由 04:00 的位图修复任务按 `t_user_signin` 重建，**可自愈** |
| 跨天零点并发 | 以服务器时间计算 `day`；跨天瞬间的两个请求分属不同的位图 offset，二者都有效 |
| 用户跨时区 | 统一按服务器时区（Asia/Shanghai）；不按用户本地时区，否则月度统计口径会分裂 |

#### 4.6.2 UC-POINTS-02 月度全勤奖励结算

| 项 | 内容 |
|---|---|
| 用例编号 | UC-POINTS-02 |
| 参与者 | 系统（定时任务）/ 管理员（手动触发） |
| 前置条件 | 上一个月已结束 |
| 后置条件 | 上月签到天数 > 25 的用户各获得一笔奖励积分，且**不会重复发放** |

**主流程**：

1. 每日 00:10 触发（`MonthlySigninBonusTask`），结算**上月**：
   ```sql
   SELECT user_id, COUNT(*) AS days
   FROM t_user_signin
   WHERE year_month = ?
   GROUP BY user_id
   HAVING COUNT(*) > 25
   LIMIT 2000
   ```
2. 对结果中**尚未发放**的用户（`NOT EXISTS` 查 `t_points_record` 的 `biz_type=2 AND biz_id=月份`），
   逐用户独立事务：`t_user_points` 加分 + `t_points_record` 记流水。
3. 管理员可通过 `POST /api/admin/points/settle-signin-bonus?month=YYYY-MM` 手动补跑历史月份。

**为什么是「每日跑上月」而不是「月末跑当月」：**

- 月末最后一刻执行，统计的是**仍在变化中**的数据；次月跑，数据已冻结，任务天然幂等
- 任务漏跑一天不会导致奖励永久丢失 —— 第二天会重跑，`uk_user_biz` 挡住已发放的部分
- 无需分布式锁：幂等性由唯一索引保证，多实例同时跑最坏情况是浪费一次查询

**为什么逐用户事务而不是批量一个事务：** 2000 个用户的批次若放在同一事务里，
会长时间持有 2000 行 `t_user_points` 的行锁。逐用户提交后，单次失败只影响一个用户，
其余用户的奖励照常发放 —— 任务的可续跑性比「要么全成功要么全失败」更有价值。

#### 4.6.3 UC-POINTS-03 积分商城兑换

| 项 | 内容 |
|---|---|
| 用例编号 | UC-POINTS-03 |
| 参与者 | 普通用户（下单）/ 管理员（商品维护与发放） |
| 前置条件 | 已登录；商品已上架；积分充足；库存充足 |
| 后置条件 | 生成兑换订单；扣积分、扣库存；管理员标记发放后订单完成 |

**主流程**：

1. 用户浏览 `GET /api/mall/goods`（仅返回上架商品），进入详情 `GET /api/mall/goods/{id}`。
2. 点击「立即兑换」→ `POST /api/mall/orders { goodsId }`：
   - 生成订单号 `M + yyyyMMdd + 6 位日内序号`（Redis `INCR`）
   - **事务内四步**：
     1. `UPDATE t_mall_goods SET stock = stock - 1, sold_count = sold_count + 1 WHERE id = ? AND stock >= 1`
        → `affectedRows = 0` 则「商品库存不足」（16005），回滚
     2. `UPDATE t_user_points SET balance = balance - ?, total_spent = total_spent + ? WHERE user_id = ? AND balance >= ?`
        → `affectedRows = 0` 则「积分不足」（16002），回滚
     3. `INSERT INTO t_mall_order (...)`（`status=0` 待发放）
     4. `INSERT INTO t_points_record (...)` 记负数流水（`biz_type=3`，`biz_id=order_no`）
3. 用户查看 `GET /api/mall/orders`（我的兑换记录）。
4. 管理员在后台标记发放 `POST /api/admin/mall/orders/{id}/finish` → 订单 `status=1`。
5. 用户可取消待发放订单 `POST /api/mall/orders/{id}/cancel` → 事务内退积分、退库存、订单 `status=2`。

**与秒杀的关键对比（为什么商城不做 Redis 预扣）：**

| 维度 | 秒杀 | 积分商城 |
|---|---|---|
| 峰值 | 万级 QPS 瞬时涌入 | 日常个位数，活动期百级 |
| 库存特征 | 超卖即资损，绝对不可接受 | 超卖同样不可接受，但**没有瞬时压力** |
| 中间态 | 有（待支付），需要 `locked_stock` | **无**，兑换即时完成 |
| 扣减手段 | Redis 预扣 + 条件 UPDATE 兜底 | **仅条件 UPDATE** |
| 引入 Redis 预扣的收益 | 挡住 99% 的无效请求 | **几乎为零**，只是多一份需要同步的状态 |

结论：商城的正确性由条件 UPDATE + 唯一索引保证，**不引入 Redis 库存**。
多一份 Redis 状态就多一份「Redis 与 DB 不一致」的可能，而这里没有换取任何性能收益。
这与「秒杀了不起缓存」是同一个判断标准：**技术手段要匹配问题规模，不是匹配技术时髦度。**

**异常与边界**：

| 场景 | 处理 |
|---|---|
| 积分不足 | 条件 UPDATE `affectedRows = 0` → 错误码 16002；**顺序上先扣库存再扣积分**，积分不足时靠事务回滚归还库存 |
| 库存不足 | 条件 UPDATE `affectedRows = 0` → 错误码 16005 |
| 商品已下架/不存在 | 下单前校验 `status=1`，否则 16003 |
| 并发兑换最后一件 | 条件 UPDATE 在行锁下串行执行，只有一个能成功，另一个拿到 `affectedRows = 0` |
| 用户连点「兑换」 | 前端按钮置灰 + 条件 UPDATE；**不设每人限购**（积分与库存本身就是约束） |
| 取消已完成的订单 | 拒绝（16007），已完成意味着商品已发出 |
| 重复取消 | 第二次取消时订单已非「待发放」，直接拒绝（16007） |
| 管理员误删商品 | 商品采用**软下架**（`status=2`）而非物理删除，历史订单仍可查看 |
| 兑换后退款导致积分为负 | 不可能——退回的是当初扣的数额，且账户列无符号 |

积分与商城是本项目**第一个区分「管理员写 / 用户读」的模块**，权限模型如下：

|---|---|---|

| 浏览上架商品 | ✅ | ✅ |

**实现约束：普通用户没有任何一条能写商城内容的路径。**

| 点赞落库延迟 | 端到端 | P99 < 1s（Redis 生效 → DB 落库） |
| 评论接口 | QPS | ≥ 500 |

| **秒杀接口** | **峰值 QPS** | **≥ 10000** |

| 首页冷启动 | 首屏时间 | < 2s（4G 网络） |

### 5.2 一致性要求

采用**分级一致性**策略，而非全局强一致：

| 数据 | 一致性级别 | 说明 |
|---|---|---|
| 用户账号、认证信息 | 强一致 | 直接读写 DB，不走缓存 |
| 帖子正文、评论内容 | 强一致 | 同步写库，写后立即读可见 |
| **点赞数、浏览数、收藏数** | **最终一致** | Redis 实时，DB 异步刷写，允许秒级延迟 |
| **秒杀库存（Redis）** | **最终一致** | 与 DB 每 5 分钟对账，以 DB 为准 |
| 消息通知 | 最终一致 | 异步生成，允许秒级延迟 |
| 热度分 | 最终一致 | 定时批量重算，5 分钟一次 |

**核心原则**：**用户能直接感知的数据用强一致，用户不能直接感知的聚合数据用最终一致。** 点赞数延迟 1 秒同步，用户完全无感；但评论内容延迟 1 秒才显示，用户会认为系统坏了。

### 5.3 可用性

| 项 | 目标 |
|---|---|
| 服务可用性 | 99.9%（年停机 < 8.76 小时） |
| 核心接口（列表、详情） | 99.95% |
| 秒杀接口 | 允许降级为「活动太火爆」，但不允许超卖或数据错乱 |
| 故障恢复时间（RTO） | < 5 分钟 |
| 数据恢复点（RPO） | < 1 分钟（MySQL 主从 + binlog） |

**关键降级策略**：

| 故障 | 降级行为 |
|---|---|
| Redis 不可用 | 帖子列表/详情降级直查 DB（限流保护）；秒杀降级为拒绝服务 |
| Kafka/RabbitMQ 不可用 | 消息堆积在本地消息表，业务接口正常返回，恢复后自动补发 |
| 下游通知服务不可用 | 通知写入失败不影响主流程，仅记日志 |
| 数据库主库不可用 | 读流量切从库，写流量返回友好错误 |

### 5.4 安全需求

| 类别 | 要求 |
|---|---|
| 认证 | JWT 双令牌（Access Token 30 分钟 + Refresh Token 7 天）；密码 BCrypt(strength=10) 加盐哈希 |
| 会话管理 | 登录态存 Redis，支持主动踢人下线；单账号异地登录告警 |
| 授权 | 接口级注解鉴权 + 资源归属校验，防止越权操作他人帖子 |
| 注入防护 | 全部使用 MyBatis 预编译参数，禁止字符串拼接 SQL |
| XSS | 正文按 Markdown 白名单渲染，HTML 输出经 Jsoup 清洗 |
| CSRF | 使用 JWT 而非 Cookie 传递凭证，天然免疫；关键操作加幂等令牌 |
| 敏感词 | DFA 自动机 + 本地词库，命中即拦截 |
| 限流 | 接口级令牌桶（Redisson RRateLimiter）；发帖 5 次/分钟、评论 20 次/分钟、秒杀按活动配置 |
| 防刷 | 秒杀同一用户 N 秒内限一次；同 IP 下单频率限制 |
| 越权下载 | 上传文件做类型白名单校验（仅 jpg/png/webp/gif），重命名存储，禁止路径穿越 |
| 数据脱敏 | 日志中手机号、邮箱、密码一律脱敏输出 |

### 5.5 可观测性

| 维度 | 方案 |
|---|---|
| 日志 | Logback + MDC 链路 ID（TraceId）；分级别输出，ERROR 单独文件 |
| 指标 | Spring Boot Actuator + Micrometer + Prometheus；自定义业务指标（点赞 QPS、MQ 消费延迟、库存余量） |
| 链路追踪 | Micrometer Tracing + Zipkin，跨 MQ 传递 TraceId（消息头透传） |
| 告警 | MQ 积压 > 10000 条、消费失败率 > 1%、Redis-DB 库存偏差 > 0、接口 P99 超阈值 |
| 健康检查 | `/actuator/health` 覆盖 DB / Redis / Kafka / RabbitMQ |

### 5.6 可扩展性

- **水平扩展**：应用无状态（会话在 Redis），可直接多实例部署。
- **数据扩展**：`t_user_like`、`t_comment`、`t_notification` 为增长最快的三张表，预留了按时间归档与分表的演进路径（详见《04-数据库设计》第 7 节）。
- **中间件可替换**：消息层抽象为统一接口，Kafka 与 RabbitMQ 实现可配置切换，新增第三种实现（如 RocketMQ）无需改动业务代码。

## 6. 约束与假设

### 6.1 技术约束

| 编号 | 约束 | 影响 |
|---|---|---|
| C-01 | 后端为单体多模块 Maven 工程 | 模块间通过接口调用而非 RPC；秒杀模块通过独立线程池 + MQ 与论坛模块做资源隔离 |
| C-02 | 必须同时实现 Kafka 与 RabbitMQ 两套异步方案 | 所有异步逻辑必须经过统一抽象层，业务代码不得直接依赖任一 MQ 的 API |
| C-03 | 秒杀采用「Redis 预扣 + MQ 异步下单」 | 用户下单后看到的是「排队中」，最终结果需轮询或推送获取 |
| C-04 | 单表数据量控制在 2000 万行以内 | 超过后触发归档或分表 |

### 6.2 业务假设

| 编号 | 假设 | 若假设不成立的后果 |
|---|---|---|
| A-01 | 校园论坛用户规模在 5 万以内，日活 < 5000 | 用户量级提升后，点赞 Bitmap 方案与单库架构需重新评估 |
| A-02 | 秒杀单场库存 < 5000，参与人数 < 5 万 | 参与人数破十万时需引入答题验证码、排队令牌等更激进的削峰手段 |
| A-03 | 秒杀活动每人限购 1 张 | 若需支持多张，`t_seckill_order` 的唯一索引必须调整 |
| A-04 | 帖子正文以 Markdown 为主，单帖不超过 5 万字 | 超大正文需考虑正文分片存储 |
| A-05 | 用户之间不存在实时聊天需求 | 若需私信，需新增会话表与 WebSocket 通道 |

## 7. 验收标准

### 7.1 功能验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AT-01 | 注册登录 | 新用户可成功注册并登录；错误密码被拒绝；Token 过期后可刷新 |
| AT-02 | 发帖 | 帖子成功发布并出现在对应板块列表首位；草稿可保存与恢复 |
| AT-03 | 点赞 | 点赞后按钮状态正确；重复点赞不报错；取消点赞后状态正确；刷新页面状态保持 |
| AT-04 | 评论 | 一级评论有正确楼层号；回复正确显示「回复 @某人」；删除后显示「该评论已删除」而非消失 |
| AT-05 | 通知 | 被评论/被点赞后收到通知；未读数正确；点击后跳转正确位置 |
| AT-06 | 秒杀 | 库存 1000、并发 10000 请求下，成功下单数**恰好等于 1000**，无超卖，无少卖 |
| AT-07 | 限购 | 同一用户重复抢购返回「已参与」，不产生第二笔订单 |
| AT-08 | 超时取消 | 下单后不支付，15 分钟后订单自动关闭，库存可被他人购买，该用户可重新参与 |
| AT-09 | MQ 切换 | 修改配置 `forum.mq.provider` 并重启后，全部异步功能正常工作，**业务代码零改动** |
| AT-10 | 签到 | 首次签到成功并加积分；**同一用户当天再次签到返回「今日已签到」，积分与流水均不增加**；跨天后可再签 |
| AT-11 | 月度全勤奖励 | 构造某用户上月签到 26 天，执行结算后该用户获得奖励且**只获得一次**；重复执行结算不重复发放；签到 25 天的用户不获得奖励 |
| AT-12 | 权限隔离 | 用普通用户 Token 调用全部 `/api/admin/mall/**` 与 `/api/admin/points/**` 接口，**逐个返回 10003**，且商城数据零变更 |
| AT-13 | 积分商城 | 兑换后积分减少、库存减少、订单与流水生成；取消后三者全部回到兑换前；积分不足或库存不足时明确报错且**不产生任何数据变更** |

### 7.2 性能验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| PT-01 | 点赞压测 | 5000 QPS 持续 5 分钟，P99 < 100ms，最终 DB 计数与 Redis 计数一致 |
| PT-02 | 秒杀压测 | 10000 并发请求抢 1000 库存，无超卖，P99 < 50ms |
| PT-03 | 帖子列表压测 | 2000 QPS，P99 < 200ms，缓存命中率 > 95% |
| PT-04 | MQ 对比 | 相同参数下产出 Kafka 与 RabbitMQ 的 QPS、P50/P95/P99、资源占用对比报告 |

### 7.3 数据一致性验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| DT-01 | 点赞对账 | 压测结束后，`SELECT COUNT(*) FROM t_user_like WHERE target_id=?` 与 Redis 计数完全相等 |
| DT-02 | 库存对账 | 活动结束后，`total_stock = available_stock + locked_stock + sold_count` 恒成立 |
| DT-03 | 消息不丢 | 压测期间人为重启消费者，重启后消息全部被处理，无遗漏 |
| DT-04 | 签到位图对账 | 手工删除某用户的位图 key 后跑修复任务，位图与 `t_user_signin` 完全一致；**积分不因修复而变化**（修复只动缓存，不动账） |
| DT-05 | 积分账目对账 | 任意时刻 `balance = total_earned - total_spent = SUM(t_points_record.change_amount)` 三者恒相等；`t_points_record` 中不存在同一 `(user_id, biz_type, biz_id)` 的重复行 |
| DT-06 | 商城库存守恒 | 任意时刻 `stock + sold_count = 初值`；已取消订单的积分与库存均已归还 |

## 8. 风险分析

| 编号 | 风险 | 等级 | 应对措施 |
|---|---|---|---|
| R-01 | 两个 MQ 都实现导致开发量翻倍 | 高 | 必须坚持统一抽象层；两套实现只写一次业务逻辑，差异收敛在 `infrastructure` 模块内部 |
| R-02 | Redis 与 DB 库存长期不一致 | 高 | 每 5 分钟对账任务 + 告警；所有库存变更操作必须同时写操作日志便于追溯 |
| R-03 | 异步落库丢失导致点赞数不准 | 中 | 本地消息表保证不丢；每日凌晨全量对账修复 |
| R-04 | 深分页导致查询变慢（如第 1000 页） | 中 | 采用游标分页（`WHERE id < lastId ORDER BY id DESC LIMIT 20`）替代 `LIMIT offset` |
| R-05 | 热点帖子被高频访问压垮单机 | 中 | 本地缓存（Caffeine）+ Redis 二级缓存；点赞数据分片到多个 Redis 实例 |
| R-06 | 敏感词库更新不及时 | 低 | 词库热加载，无需重启；结合用户举报人工复核 |
| R-07 | 秒杀开始瞬间的缓存预热失败 | 中 | 预热任务失败自动重试；提供后台手动预热入口；预热未完成时活动自动置为不可用 |
| R-08 | 首次压测数据不具备可比性 | 中 | 严格固定变量（见《05-消息中间件选型对比方案》第 5 节），每轮压测重复 3 次取中位数 |
